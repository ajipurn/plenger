# Contributing to plenger

plenger is a local-first security tool. Keep its safety invariants intact: never
execute or import target repository code, never fall back from an isolated worker
to the host, never publish the package or images, and treat repository
configuration, target responses and model output as untrusted input. The product
contract lives in [docs/SPEC.md](docs/SPEC.md); architecture decisions live in
[docs/adr](docs/adr).

## Setup

Requirements: Python 3.12.4 or newer 3.12 (`.python-version` pins 3.12.13), uv,
Docker for the parser worker and container scanners, and Node only when changing
the dashboard.

```sh
make install
```

## Repository layout

```text
src/plenger/
  cli/main.py        Typer CLI (`plenger`, also `python -m plenger`)
  api/               Loopback HTTP API: app.py routes, schemas.py bodies, pairing.py
  services/          Use cases shared by CLI and API
    application.py     static scan runs, recovery and engine capabilities
    findings.py        paged finding reads, signed cursors, lifecycle updates
    reports.py         stored reports, graph pages and exports
    evidence.py        evidence retention expiry; ci_gate.py maps reports to exit codes
    scanners/          managed scanner manifest, OSV database, setup and baseline runs
    active/            active-run plans, broker process, confined worker and runs
    assessment.py      non-authoritative finding assessment
  domain/            Strict contracts: base model, config, run states, parser output
  policy/            Redaction, consent scopes and active-test scope rules
  storage/           SQLite store (database.py), Alembic migrations, retention, backups
  adapters/          Isolated engines: Docker Python parser (python_parser.py), Promptfoo
    scanners/          Semgrep/OSV/Trivy contracts, normalization, containers, execution
  broker/            DNS-pinned request dispatch and its job-scoped Unix socket IPC
  runner/            Fixed OWASP LLM cases, trusted observers, confined worker/sandbox
  evaluators/        Non-authoritative assessment rubric, models and providers
  graph/worker.py    Stdlib-only parser mounted into the isolated container
  ui/                Built dashboard assets (generated by `make ui-build`)
web/                 Dashboard source (React, TypeScript, Vite) and Playwright E2E
tests/               unit/, security/ and integration/ suites
scripts/             Release smokes, benchmarks and the dependency ledger check
docs/                PRD, SPEC, ADRs, status and recorded evidence
examples/, fixtures/ Configuration examples and synthetic test fixtures
```

Package `__init__.py` files only describe the package. Import from the concrete
module (`from plenger.storage.database import open_store`) so code location and
monkeypatch targets stay unambiguous.

## Everyday commands

```sh
make lint          # ruff check + format check
make format        # apply safe ruff fixes and formatting
make typecheck     # mypy --strict (files configured in pyproject.toml)
make test-fast     # Python tests except integration
make test          # full Python suite
make ui-build      # type-check and bundle the dashboard into src/plenger/ui
make ui-test       # dashboard unit tests
make e2e           # browser E2E against a disposable project
make build         # wheel and sdist
make check         # full local gate (scripts/check.sh)
```

Tests are marked by directory (`unit`, `security`, `integration`), so markers such
as `-m "not integration"` work with plain `pytest`. Integration tests report
skipped/blocked, never passed, when Docker, an image or a scanner is unavailable.

Browser E2E uses an installed local Chrome/Chromium binary and a disposable
plenger project plus mock target. Set `PLENGER_E2E_BROWSER` to an explicit
browser path when the default is not discoverable; without a browser, the test
reports an explicit environment skip rather than a product pass.

Untuk smoke rilis scanner yang reproducible dan tanpa network, pastikan tiga image
digest sudah tersedia lalu jalankan:

```sh
uv run --locked python scripts/check_scanner_images.py
```

Perintah ini memverifikasi ketiga digest, menjalankan Semgrep dan Trivy pada source
produksi dengan container read-only/non-root/network-none, lalu gagal jika ada
temuan. Image OSV hanya diverifikasi keberadaannya; database OSV tetap harus
diprovisionkan melalui `provision-osv-db` secara eksplisit.

Untuk memverifikasi dependency controls OSV secara nyata, termasuk vulnerable/fixed
dan requirement tanpa pin atau dengan range, jalankan smoke berikut. Perintah ini
memakai temporary workspace dan melakukan provisioning database sebagai satu-satunya
langkah network-enabled; empat scan setelahnya offline:

```sh
uv run --locked python scripts/check_osv_scanner.py
```

Integration tests use the pinned local Docker image and no hosted API. They report
**skipped/blocked**, not passed, when the image/runtime is absent. For the local
quality gate—including the explicit network-enabled OSV provisioning smoke—run
`scripts/check.sh`. The OSV smoke still keeps its network access limited to the
explicit database setup phase; all scanner cases after provisioning are offline.

## Conventions

- Database changes are new Alembic revisions under
  `src/plenger/storage/migrations/versions/`; `downgrade()` raises, because
  rollback uses `plenger backup`/`restore` instead of destructive downgrades.
- Rebuild and commit `src/plenger/ui` whenever `web/src` changes, so installs do
  not need Node.
- Record behaviour changes in the relevant ADR and in `docs/IMPLEMENTATION_STATUS.md`
  and `docs/TEST_RESULTS.md`, using only results that were actually run.
- Give each module one responsibility. When one outgrows it, split it into a
  subpackage (see `services/scanners/`) and patch tests at the module that
  performs the lookup, not where the name is defined.
- Keep commits focused on one topic; each commit should pass `make lint`,
  `make typecheck` and `make test`.
